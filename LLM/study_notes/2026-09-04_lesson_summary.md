## 오늘의 핵심 한 문장

오늘 수업은 **LangGraph를 이용해 “검색형 에이전트 → 관리자형 멀티 에이전트 → SQL 질의 에이전트”로 점점 더 복잡한 자동화 흐름을 만드는 법**을 배우는 시간이었다.

---

## 전체 수업 흐름

오늘의 흐름은 단순한 RAG에서 시작해서, 역할 분담이 있는 멀티 에이전트, 그리고 데이터베이스를 안전하게 조회하는 SQL Agent까지 확장됩니다.

1. **Agentic RAG**
   - 문서를 검색하고
   - 검색 결과를 평가하고
   - 필요하면 질문을 다시 써서
   - 다시 검색한 뒤 답변하는 흐름을 만든다

2. **Supervisor 멀티 에이전트**
   - 관리자 에이전트가
   - Researcher와 Coder 중 누가 다음에 일할지 결정한다
   - 작업이 끝나면 FINISH로 종료한다

3. **SQL Agent**
   - SQLite DB를 탐색하고
   - SQL을 생성하고
   - 실행 전 사람이 승인하는 HITL까지 적용한다

즉, 오늘은 **“LLM이 단독으로 답하는 방식”에서 “도구와 상태를 활용해 협업하는 방식”으로 발전하는 흐름**을 배웠습니다.

### 1) `08_langgraph/02_multi_agent/01_agentic_rag.ipynb`

#### 학습 목표
이 노트북은 **LangGraph로 Agentic RAG(검색 → 생성 → 재질문 → 재검색)** 흐름을 만드는 실습입니다.  
일반 RAG보다 한 단계 더 나아가, **LLM이 스스로 검색 도구를 쓸지 판단하고, 검색 결과가 부족하면 질문을 다시 바꿔 재검색하는 구조**를 만듭니다.

#### 실행 흐름
1. OpenAI/LangSmith 환경변수 설정
2. 웹 문서 로드
3. 문서 청킹
4. 임베딩 후 벡터스토어 생성
5. Retriever 생성
6. 검색 Tool 만들기
7. LLM이 Tool 호출할지 판단
8. 검색 결과 평가
9. 부족하면 질문 재작성
10. 최종 답변 생성
11. LangGraph로 전체 흐름 연결
12. `graph.stream()`으로 중간 과정 확인

#### 핵심 포인트
- `WebBaseLoader`로 웹 문서를 읽는다
- `RecursiveCharacterTextSplitter`로 긴 문서를 잘게 나눈다
- `InMemoryVectorStore` + `OpenAIEmbeddings`로 검색 가능한 벡터 저장소를 만든다
- `@tool`과 `ToolNode`로 검색 함수를 LLM 도구로 연결한다
- `StateGraph`로  
  **질문 → 검색 → 평가 → 재작성/답변** 흐름을 분기시킨다
- 평가 로직은 **`state["messages"][0]`(원 질문)과 `state["messages"][-1]`(최근 검색 결과)**에 의존하므로, 메시지 순서가 바뀌지 않도록 주의해야 한다

#### 실행 시 주의점
- 검색 결과 판단은 메시지의 위치를 기준으로 하므로, 중간에 불필요한 메시지가 끼면 평가가 어긋날 수 있다
- `state["messages"]`의 첫 메시지와 마지막 메시지가 각각 무엇인지 확인하면서 디버깅해야 한다
- 질문이 모호할수록 재질문 루프가 자주 발생할 수 있다

#### 이해해야 할 흐름
- 검색이 필요한 질문인지 먼저 판단
- 검색 결과가 질문과 관련 있는지 평가
- 결과가 부족하면 질문을 다시 쓰고 재검색
- 그래프가 반복적으로 돌아가며 답변 품질을 높임

#### 셀 단위로 따라가기
- 환경변수 설정 셀 실행
- 웹 문서 로드 셀 실행
- 문서 분할 셀 실행
- 벡터스토어/리트리버 생성 셀 실행
- 검색 Tool 연결 셀 실행
- 평가용 체인 실행 셀 확인
- 그래프 구성 셀 실행
- `graph.stream()` 실행 셀에서 중간 상태 출력 확인

### 2) `08_langgraph/02_multi_agent/02_supervisor.ipynb`

#### 학습 목표
이 노트북은 **Supervisor(관리자) 에이전트가 Researcher / Coder 작업자를 조정하는 멀티 에이전트 구조**를 다룹니다.  
핵심은 “하나의 에이전트가 모든 걸 해결하는 것이 아니라, 역할을 나눠 협업하게 만든다”는 점입니다.

#### 실행 흐름
1. OpenAI/Tavily/LangSmith 환경 설정
2. Tavily 검색 도구와 PythonREPLTool 생성
3. Researcher/Coder 에이전트 생성
4. Supervisor가 다음 작업자를 선택하도록 구조화 출력 설정
5. `StateGraph`로 Supervisor ↔ 작업자 흐름 구성
6. 질문에 따라 Researcher 또는 Coder가 실행
7. Supervisor가 다음 노드를 결정
8. `FINISH`면 종료

#### 핵심 포인트
- `Supervisor`는 실제 일을 하지 않고 **조율만** 한다
- `Researcher`는 검색 도구를 사용한다
- `Coder`는 파이썬 코드를 실행한다
- `RouteResponse(next=...)`로 다음 행동을 제한한다
- `next`는 그래프 상태의 핵심 값으로 취급되며, `conditional_map`이 이 값을 보고 다음 노드를 고른다
- `add_messages`를 사용해 대화 기록을 누적한다
- 작업자 에이전트의 출력은 다시 대화 흐름에 넣기 위해 **HumanMessage 형태로 포장**되는 구조를 사용한다

#### 왜 HumanMessage로 반환하나?
작업자 에이전트가 내놓은 결과를 그대로 “도구 출력”처럼 두기보다,  
**다음 에이전트가 이전 대화의 일부로 자연스럽게 읽게 하려는 목적**이 있습니다.

즉,
- Supervisor가 지시하고
- 작업자가 실행한 뒤
- 그 결과를 다시 **대화 메시지**로 돌려줘야
- 다음 단계의 LLM이 문맥을 이어받아 판단할 수 있습니다.

#### 상태 전이와 분기 구조
- `next` 값을 상태에 넣는다
- Supervisor의 출력 `next`를 기준으로 분기한다
- `conditional_map`이 `"Researcher"`, `"Coder"`, `"FINISH"` 같은 값을 실제 노드 이름으로 연결한다
- 이 구조 덕분에 Supervisor가 말한 대로 그래프가 다음 행동을 선택한다

#### 이해해야 할 흐름
- 질문을 보면 Supervisor가 “누가 먼저 일해야 하는지” 판단
- 작업자 에이전트가 실행 후 다시 Supervisor에게 돌아옴
- 필요하면 다른 작업자가 이어서 작업
- 최종적으로 FINISH로 종료

#### 셀 단위로 따라가기
- 환경변수 설정 셀 실행
- Tavily 키와 PythonREPL 도구 준비 셀 실행
- Researcher/Coder 정의 셀 실행
- Supervisor 구조화 출력 셀 실행
- `conditional_map`이 어떻게 연결되는지 확인
- 그래프 실행 셀에서 에이전트 순환 확인
- 출력이 `HumanMessage`로 합쳐지는지 확인

### 3) `08_langgraph/02_multi_agent/03_sql_agent.ipynb`

#### 학습 목표
이 노트북은 **SQLite DB(Chinook.db)를 대상으로 SQL Agent를 만들고, 중요한 쿼리 실행은 사람 승인(HITL) 후 진행하는 방법**을 다룹니다.

#### 실행 흐름
1. OpenAI/LangSmith 환경 설정
2. Chinook.db 다운로드
3. `SQLDatabase`로 DB 연결
4. 테이블 목록과 샘플 쿼리 확인
5. `SQLDatabaseToolkit`으로 SQL 도구 생성
6. `create_agent`로 SQL Agent 생성
7. 질문 입력 후 스트리밍 실행
8. HITL 미들웨어로 `sql_db_query` 전 실행 중단
9. 사람이 승인
10. `Command(resume=...)`로 재개
11. 최종 답변 출력

#### 핵심 포인트
- 에이전트는 먼저 테이블 목록을 확인해야 한다
- 그 다음 관련 스키마를 보고 SQL을 만든다
- SQL 실행 전에 재확인하고, 에러가 나면 재시도한다
- DML(`INSERT`, `UPDATE`, `DELETE`, `DROP`)은 금지한다
- `HumanInTheLoopMiddleware`로 안전장치를 둔다
- DB 연결 직후에는 단순히 에이전트만 만드는 것이 아니라, **테이블 확인 → 간단한 조회 테스트 → 도구 구성 → 에이전트 생성** 순서를 따라가며 중간 셀을 확인해야 한다

#### 중간 실행 단계에서 확인할 것
- `SQLDatabase.from_uri()`가 정상 연결되는지 확인
- `db.get_usable_table_names()`로 사용 가능한 테이블을 보는지 확인
- `db.run("select * from ... limit 5")` 같은 샘플 쿼리가 동작하는지 확인
- `SQLDatabaseToolkit`이 DB와 연결된 도구들을 제대로 만드는지 확인
- 에이전트 생성 후 바로 질의하지 말고, 먼저 도구가 정상적인지 점검

#### 이해해야 할 흐름
- DB 질문이 들어오면 에이전트가 스키마를 탐색
- 적절한 SQL을 생성
- 실행 직전에 사람이 승인 가능
- 승인 후 실행하고 결과를 자연어로 답변

#### 셀 단위로 따라가기
- DB 파일 다운로드 셀 실행
- `SQLDatabase` 연결 셀 실행
- 테이블 목록 확인 셀 실행
- 샘플 쿼리 실행 셀 실행
- toolkit 생성 셀 실행
- agent 생성 셀 실행
- 스트리밍 실행 셀 확인
- HITL 중단 지점에서 SQL 내용 확인
- 승인 후 `Command(resume=...)` 재개 셀 실행

## 핵심 코드와 개념

---

### 1. LangGraph 기본 구조
세 노트북 모두 공통적으로 **그래프 기반 실행 흐름**을 사용합니다.

- `StateGraph`: 상태 기반 그래프 정의
- `START`, `END`: 시작과 종료
- `add_node()`: 노드 추가
- `add_edge()`: 순차 연결
- `add_conditional_edges()`: 조건 분기

이 구조 덕분에 단순 함수 호출보다 복잡한 흐름을 관리하기 쉬워집니다.

---

### 2. 메시지 상태 관리
- `MessagesState`
- `AgentState`
- `add_messages`

메시지를 리스트로 누적하면서 이전 대화 내용을 계속 참고할 수 있게 합니다.  
멀티 에이전트나 재질문 흐름에서는 이 상태 관리가 매우 중요합니다.

---

### 3. Tool 사용
- `@tool`
- `ToolNode`
- `bind_tools()`
- `tools_condition`

LLM이 직접 검색하거나 계산하는 게 아니라, **도구를 호출하고 그 결과를 다시 받는 방식**입니다.

예:
- RAG에서는 검색 함수
- Supervisor에서는 Tavily 검색, Python 실행
- SQL Agent에서는 DB 조회 도구

---

### 4. 구조화 출력
- `with_structured_output()`
- Pydantic `BaseModel`
- `Literal`

Supervisor나 문서 평가처럼 **반드시 정해진 형식으로 답해야 하는 경우**에 사용합니다.

예:
- `next`: `"Researcher" | "Coder" | "FINISH"`
- `binary_score`: `"yes" | "no"`

이렇게 하면 그래프 분기가 안정적입니다.

---

### 5. 검색과 벡터 저장
Agentic RAG에서 사용한 개념입니다.

- `WebBaseLoader`: 웹 문서 로드
- `RecursiveCharacterTextSplitter`: 문서 청킹
- `OpenAIEmbeddings`: 임베딩 생성
- `InMemoryVectorStore`: 벡터 저장
- `as_retriever()`: 검색기 변환

문서를 잘게 나누고 임베딩한 뒤, 질문과 유사한 문서를 찾아 답변에 활용합니다.

---

### 6. SQL Agent 안전장치
- `SQLDatabase`
- `SQLDatabaseToolkit`
- `HumanInTheLoopMiddleware`
- `InMemorySaver`
- `Command(resume=...)`

SQL은 잘못 실행하면 위험할 수 있으므로,  
실행 전 승인 및 상태 복원을 통해 안전하게 제어합니다.

## 이전 학습과의 연결

오늘 수업은 LangChain/LangGraph 학습의 자연스러운 확장입니다.

1. **기본 RAG에서 출발**
   - 문서를 검색해서 답변하는 구조를 배웠다면,
   - 오늘은 그걸 더 발전시켜 **검색 품질을 판단하고 재시도하는 Agentic RAG**로 확장했습니다.

2. **단일 에이전트에서 멀티 에이전트로 확장**
   - 하나의 LLM이 모든 일을 하는 방식에서,
   - Supervisor가 역할을 나누는 **업무 분담형 구조**로 넘어갔습니다.

3. **일반 에이전트에서 안전한 업무 자동화로 확장**
   - 검색이나 코드 실행뿐 아니라,
   - 실제 DB를 다루는 SQL 작업까지 연결했으며,
   - HITL로 위험한 실행을 사람이 통제하게 했습니다.

즉, 오늘 수업은 **“도구를 쓰는 LLM” → “상태를 가진 에이전트” → “협업하고 검증하는 에이전트 시스템”**으로 이어지는 흐름입니다.

## 포트폴리오 회고 포인트

이번 수업은 포트폴리오 회고에 아주 좋습니다.  
단순히 “코드를 실행했다”가 아니라, **어떤 설계 판단을 했는지**를 보여줄 수 있기 때문입니다.

### 1. 문제 해결 구조를 만들었다
- 검색이 필요한 질문을 자동으로 처리
- 검색 결과가 부정확하면 질문을 다시 바꿔 재시도
- 단순 답변이 아니라 **자기 수정형 흐름**을 설계

### 2. 역할 분담형 AI 시스템을 이해했다
- Supervisor가 작업을 분배
- Researcher는 검색
- Coder는 코드 실행
- 이 구조는 실제 업무 자동화에 가깝다

### 3. 안전성을 고려했다
- SQL 실행 전 승인
- 위험한 DML 금지
- 상태 저장 및 재개
- 실무에서 중요한 **가드레일 설계**를 배웠다

### 4. LangGraph의 강점을 체감했다
- 단순 체인보다 복잡한 흐름을 표현하기 쉬움
- 조건 분기와 반복이 자연스럽다
- 상태 기반 디버깅이 가능하다

### 5. 초보자에서 한 단계 올라갔다
오늘 수업은 그냥 “LLM 쓰기”가 아니라,
- 도구를 붙이고
- 상태를 관리하고
- 분기와 승인 흐름을 설계하는 단계로 넘어갔다.

# 정답과 해설

## 1번 정답: B
**해설:** Agentic RAG는 단순히 검색만 하는 것이 아니라, 검색 결과가 충분한지 평가하고 부족하면 질문을 다시 써서 재검색하는 흐름을 포함합니다.

---

## 2번 정답: C
**해설:** Supervisor는 실제 작업을 수행하기보다 Researcher와 Coder 중 누가 다음에 일할지 결정하는 조정자 역할을 합니다.

---

## 3번 정답: B
**해설:** SQL은 잘못 실행하면 위험할 수 있으므로, 실행 전에 사람이 승인하도록 해서 안전장치를 둡니다.

## 4번 정답:
**질문 입력 → 검색 수행 → 검색 결과 평가 → 질문 재작성 → 답변 생성**

**해설:** 먼저 질문을 받고 검색한 뒤, 결과가 부족하면 질문을 다시 바꿔 재검색하고 최종 답변을 만듭니다.

---

## 5번 정답: B
**해설:** `next`는 다음에 어떤 노드로 이동할지 정하는 상태 값입니다. Supervisor의 판단 결과를 그래프 분기에 사용합니다.

## 6번 예시 답안:
에이전트는 먼저 질문을 보고 어떤 테이블이 필요할지 추측한 뒤, 테이블 목록과 스키마를 확인합니다. 그 다음 적절한 SQL을 생성하고, 실행 전에 필요하면 사람이 승인한 후 결과를 조회합니다. 마지막으로 조회 결과를 자연어로 답변합니다.

**해설:** SQL Agent는 바로 쿼리를 실행하는 것이 아니라, 스키마 탐색 → SQL 생성 → 실행 → 답변의 순서로 동작합니다. HITL이 있으면 실행 전에 중단되어 승인 절차를 거칩니다.

> 자동 검토 메모: 대체로 잘 정리되었지만, 원본 파일별 분석과 비교했을 때 몇 가지 실행/사실 정확도 보완이 필요합니다. 1) `03_sql_agent.ipynb`에서 원문에는 DB 연결 테스트와 에이전트 구성에 더해 여러 중간 셀/추가 설명이 있는데, 통합 보고서는 흐름 위주로만 정리되어 일부 실행 단계의 세부가 누락되었습니다. 2) `02_supervisor.ipynb`의 에이전트 메시지 포장 방식(HumanMessage로 반환하는 이유)과 상태 전이 설명은 잘 담겼지만, 원문 기반으로 보면 `next`를 상태에 두는 구조와 `conditional_map`의 연결이 더 명시적으로 드러나야 합니다. 3) `01_agentic_rag.ipynb`와 `03_sql_agent.ipynb`에서 사용된 모델명이 `gpt-5.4-mini`, `gpt-5.6-luna`처럼 원문에 따라 다를 수 있는데, 통합 보고서에서는 특정 모델명을 단정적으로 쓰는 부분이 있어 자료 불일치 위험이 있습니다. 4) `01_agentic_rag.ipynb`의 `state['messages'][0]`, `state['messages'][-1]` 기반 평가 로직처럼 실행 시 메시지 위치에 의존하는 중요한 주의점이 보고서에 더 분명히 반영되면 좋습니다. 5) 각 파일별로 ‘다음에 무엇을 실행해야 하는지’는 전반적으로 있으나, 초보자가 바로 따라 하기 위한 셀 단위 체크포인트가 일부 더 구체적이면 좋겠습니다. 핵심 요약과 전체 흐름은 충실하지만, 위 세부 사항을 보완하면 기준을 더 안정적으로 만족합니다.
